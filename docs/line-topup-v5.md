# PAIR LIVE V5: one-tap LINE top-up review and member notice

This change keeps `decideTopup()`, legacy balance updates, wallet ledger and audit logic unchanged. The member still creates a top-up request in the web app. The admin LINE card has a postback Quick Reply for approve/reject. The admin must check the payment evidence through the channel actually received (LINE, SMS, bank or another approved process) before tapping. The card does not require a slip upload. There is no second confirmation card and no admin chat response.

LINE does not let an application edit a previously delivered Flex Card to remove its buttons. New cards place actions in Quick Reply, which LINE normally removes from the chat view after a reply. Cards sent by older versions may still show embedded buttons; a valid old review action now follows the one-tap decision path. Old signed confirmation actions are ignored.

The webhook route verifies the raw LINE signature before passing events to the postback processor. The processor checks the admin LINE user ID against the server allowlist and active admin identity, then calls `decideTopup()` only for a pending request. The existing request lock and audit uniqueness decide the balance once. A webhook event ID and chat-action audit record support retry handling. No response message is pushed to the admin chat.

When the request is approved, the processor creates a single `member_topup_member_notifications` row keyed by `request_id`. It resolves the member's LINE user ID from `member_identities`, requiring `provider='line'`, the configured LINE Login channel ID and the request's internal `member_id`. It never treats the member UUID as a LINE user ID and excludes configured admin recipients. If no eligible LINE identity exists, the outbox records `FAILED`; the approved balance is unchanged. A rejected or pending request has no member delivery.

The outbox worker sends `✅ เติมจำนวน XXXX แต้มที่ต้องการแล้ว` using the approved database amount. A successful Messaging API response marks `SENT`, meaning LINE accepted the push, not that the member opened it. Temporary errors become bounded exponential retries; a permanent error becomes `FAILED`. Claims use `FOR UPDATE SKIP LOCKED`, short leases and a stable LINE retry key based on `request_id`. A concurrent worker cannot claim the same row. The 23-hour retry window stays within the LINE retry-key horizon. The worker also runs immediately after a webhook commit. The existing private notification worker and guarded admin retry endpoint can resume work after a crash or LINE outage. A repeated webhook/request cannot create a second outbox row or increment the balance again.

The member notice is enqueued after `decideTopup()` succeeds, in a separate database transaction. If the process stops between the approved commit and the enqueue, the next webhook redelivery or repeated admin action detects the already approved request and creates the missing row. This is a recoverable gap, so LINE webhook retries and the private worker must remain enabled. Do not describe notification delivery as atomic with the balance commit or as proof of member read.

## Migration and activation

`migrations/015_topup_member_line_outbox.sql` adds only the member LINE outbox. It does not change balances or ledger. The migration runner and schema table allowlist include it. Apply through the reviewed test/staging process first. Before any production migration, back up the database, inspect the target and migration history, review the forward SQL, and confirm the private worker/LINE configuration. The approval path checks for the outbox table before approving; when missing, it returns a service error instead of creating an approved request that cannot queue a notice. Do not use a production request to test the new flow.

No new environment variable is needed. The flow reuses `LINE_MESSAGING_CHANNEL_ACCESS_TOKEN`, `LINE_LOGIN_CHANNEL_ID`, `LINE_LOGIN_PROVIDER_ID`, `LINE_MESSAGING_PROVIDER_ID`, `LINE_MESSAGING_CHANNEL_ID`, `LINE_MESSAGING_CHANNEL_SECRET`, and `ADMIN_AUTH_ALLOWLIST_JSON` according to the existing provider setup. Admin card delivery needs the Messaging API token and server allowlist. Approval needs the verified webhook signature plus active admin identity. Member delivery needs the Messaging API token and an eligible LINE identity for that member. Provider pairing remains an approval precondition; it is not a gate on sending the admin card.

## Test boundary

Tests use a local isolated `pair_live_migration_test` PostgreSQL database and a fake `fetch` for LINE Messaging API. They cover card format, signature rejection, direct approval, denied admin, duplicate/concurrent postbacks, exact member recipient, no second/admin message, missing LINE identity, retry after a simulated LINE 503, rejected requests, migration and existing history/CSV behavior. They do not send to real LINE, verify OA friendship/recipient eligibility, or observe the Quick Reply animation in the LINE client. Vercel build/deployment and production migration are separate operational checks.
