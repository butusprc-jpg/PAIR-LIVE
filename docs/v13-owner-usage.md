# V13 Owner Usage Dashboard

Route: `/owner` → `มิเตอร์การใช้งาน`. Server endpoints: `GET /api/owner/usage`, `POST /api/owner/usage/alerts`. Both require the existing owner session. Settings additionally require the one-time owner CSRF challenge. No shop admin or member session authorizes these routes. Rate limit: 20 reads per owner session per minute per instance; abuse protection across instances should also be configured at the edge before public rollout.

Migration `030_owner_usage_metrics.sql` is an independent extension of the V8–V11 base. The manifest appends 030 after 027; 028 and 029 remain reserved for V12. The migration runner permits only 028/029 to arrive before an installed 030 when the branches are combined; resolve the manifest to include V12 files and run migration validation on an isolated test database before any production rollout. No existing migration is edited. `schema_migration_history` still uses full file path and SHA-256.

The system currently has a single verified OA binding. Only that OA gets member counts (distinct LINE member identities for the configured login channel), round counts (all epochs by actual round date), and LINE usage (a token whose SHA-256 matches the verified binding). Unconnected OAs show null/UNAVAILABLE, never fabricated zero. The LINE quota API is read only, with a five-minute in-process cache and error state. Its consumption is approximate and quota accounting does not equal every chat message. No LINE message is sent to test usage. A quota type of `none` has no finite remaining count.

API request counts are instrumented only for authenticated member API routes that use `currentMember()`. The server batches 25 requests into a single Neon transaction, with no body, token, cookie or headers stored. Counts are **PARTIAL**: instances may shut down before a batch of fewer than 25 flushes, and routes that do not use `currentMember()` are outside scope. This is not a billing meter. The sole OA binding is chosen server-side after authentication; the client cannot choose its OA. There is no stream or YouTube watch-time measurement, so no such duration is displayed.

Owner reads create daily snapshots when they have actual data: connected OA member count, existing round dates across epochs, current-month LINE API consumption, and batched measured API requests. Missing history stays missing. The dashboard supports 7/30 day views and quota alert thresholds at 70/85/95/100; alert setting changes are audited. Alerts stay inside the dashboard. No background LINE push is used.

Vercel Function Invocations and Bandwidth, Neon Storage and Compute display `UNAVAILABLE` with dashboard links because no scoped usage API is wired or authorized here. These are shared resources, never allocated to an OA as a cost. To activate in production later: confirm the owner auth account, OA binding, LINE token, migration history through 027, and isolated PostgreSQL test results; install 030 only after backup and separate approval. Do not run it on production during development.
