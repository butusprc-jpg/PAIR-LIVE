# V14.8 Railway release preparation (no production changes)

## Current topology and limits

The current `railway.json` belongs to the existing **round worker**; leave its one-replica start command unchanged. Create a separate **web** service from this repository and use `Dockerfile.railway-web`. `railway.web.json` records the intended web settings for review and tests. Railway's legacy config-as-code is being retired; a new service must apply these settings in Railway's service UI or its current Infrastructure as Code workflow, not assume this second JSON is selected automatically. Disable automatic production deployment on both services until cutover approval. Do not run the test-only `db:migrate` command as a Railway pre-deploy command.

The application currently binds a single connected OA with `CONNECTED_LINE_OA_ID` and one server-side Messaging token per process. Owner reporting can list more OAs, but a single web/worker deployment cannot safely route arbitrary OA webhooks and actions to different credentials. Multi-OA production serving requires a reviewed credential-routing design, authorization and isolation tests before enabling further OAs. Do not create speculative tokens or copy the same token across OAs.

## Staging service setup

1. Create a Railway **separate staging project/environment**, with a disposable Neon test branch/database and synthetic LINE/test credentials only. Keep GitHub autodeploy off. Web service uses `Dockerfile.railway-web` (Dockerfile path), Docker builder, start command `node server.js` (image default), one replica, `/api/health/ready`, 120-second startup health timeout, `ON_FAILURE` restart with 10 retries. Set `PORT` via Railway injection and listen on `0.0.0.0`. Never use serverless sleep for the round worker; its scheduled process must stay awake. Logs go to stdout/stderr, with no request bodies, session cookies, access tokens or slip data.
2. Keep the old worker `railway.json` for its existing service. The web Dockerfile is deliberately non-default so it cannot hijack the worker's Nixpacks build. Keep notification delivery and cleanup disabled until separately reviewed. No cron is configured for this web service. The health route checks `SELECT 1` and returns only `ready` or `unavailable`; it does not run migrations or trigger transactions.
3. Set public **build arguments** `NEXT_PUBLIC_LINE_LIFF_ID` and `NEXT_PUBLIC_APP_BASE_URL` for the web image, and set the same names at runtime. Next.js embeds `NEXT_PUBLIC_*` at build time; changing runtime values alone needs a rebuild. Set `NODE_ENV=production`, `DATABASE_URL` from the isolated Neon test branch with TLS validation, and server-only LINE Login/Messaging/Provider IDs, channel secrets/token, `CONNECTED_LINE_OA_ID`, `ADMIN_AUTH_ORIGIN`, `ADMIN_AUTH_ALLOWLIST_JSON`, `TOPUP_IMAGE_SIGNING_SECRET`, R2 credentials, and `VDO_REMOTE_ENCRYPTION_KEY` only where the feature is enabled. Use Railway secret variables, never Docker build args for private values. Start with `NOTIFICATION_DELIVERY_ENABLED=false`, `TOPUP_CLEANUP_ENABLED=false`, `PAIR_WALLET_CUTOVER_VERIFIED=false` unless reviewed existing settings require otherwise; never change wallet cutover as part of hosting migration.
4. Keep Neon as the database; do not migrate its data. Use the correct **test** branch URL in staging, preferably its pooled endpoint after testing transaction-scoped RLS, locks, and idempotency. `pg` uses a per-process pool of 5 connections, 5-second connect timeout, 30-second idle timeout and verified TLS for non-local URLs. The separate round worker also has a pool; inspect `pg_stat_activity` and Neon connection limits per replica before scaling. Other optional reset pools add connections. A pooled URL is not a substitute for testing all transaction and advisory-lock paths. Deploy web and worker in a region near the Neon endpoint, then measure latency.
5. Use a staging HTTPS domain and matching staging LIFF Endpoint URL, Login callback, Messaging webhook, Rich Menu target, `ADMIN_AUTH_ORIGIN`, and public app base URL **only with staging LINE channels**. Retain the production LIFF/Rich Menu/webhook URLs on Vercel. Cookies remain HttpOnly, Secure on production Node, SameSite=Lax, with server-side 12-hour or fixed 30-day remembered sessions. Confirm account switch, logout, expiry, rotation, mobile LINE in-app browser, and external QR before any production DNS change. The signed top-up image origin uses the configured app base URL and must be publicly reachable by LINE without exposing R2.
6. Test VDO.Ninja start/stop, member countdown, round worker singleton behavior, wallet/ledger, topup/withdrawal replay, settlement, RLS, and tenant isolation with synthetic accounts. The Docker runtime includes ImageMagick and Tesseract for existing gated OCR paths; this does **not** enable automatic OCR point decisions. Use only an authorized staging camera/LINE account; otherwise mark those flows NOT TESTED.

## Production cutover and rollback (approval required later)

1. Inventory live environment variable **names** and values in each authorized secret manager, verify Neon grants/history/checksums and backup status, current webhook URL, LIFF Endpoints, DNS TTL and signed-image links. Back up Neon using the approved procedure; do not run a migration merely for the hosting change. Confirm Railway staging measurements, line preflight, health and business regression before approval.
2. Prepare a production Railway web image from the reviewed SHA with production public build args, but keep it private and without public traffic. Configure HTTPS domain, secrets, one web replica, and avoid running a second round worker against the same production database. If production hosting demands schema changes, review and apply them separately through the approved migration path; `scripts/migrate.ts` intentionally refuses production.
3. In a short coordinated window, make exactly one worker active and switch the HTTPS origin/LINE webhook/Rich Menu/LIFF Endpoint and authorized callbacks to the reviewed Railway domain. Check domain certificate, LINE signature and replay behavior, Secure cookies, LIFF login, webhook receipt, signed QR/slip links, member session, round state and financial audit. Existing cookies scoped to the old host cannot automatically cross to a new domain; users may need to log in once. To minimize that disruption, use a controlled custom domain shared between deployments when available.
4. For rollback, stop Railway worker first, reactivate the single Vercel-era worker, restore old webhook/LIFF/Rich Menu/callback targets and DNS, and keep the original Vercel deployment and Neon unchanged. Confirm old host works and audit no duplicate round/credit actions; old signed links may remain valid until expiry. Never run both workers at once. Record old/new SHA, settings, cutover time and test results without logging secrets.

## Cost and capacity model (USD, not measured usage)

As of November 2026, Railway documents Hobby as **$5 monthly minimum including $5 usage**, Pro as **$20 including $20**, RAM **$10/GB-month**, CPU usage **$20/vCPU-month**, and egress **$0.05/GB**. These are billing rates, not an invoice estimate. For a continuously awake web service plus worker, monthly metered usage is `RAM GB-hours × published RAM rate + CPU vCPU-hours × published CPU rate + egress GB × $0.05`; charge is at least the plan minimum. A 0.5-GB resident web container alone implies about **$5/month RAM** at full-month occupancy before the worker, CPU, egress and Neon. This is a *scenario*, not a measured footprint. Serverless sleep could reduce web idle time but adds wake latency; do not sleep the worker. Restarts/overlaps can temporarily raise use.

Vercel Hobby currently lists a free-tier allowance for 1,000,000 function invocations, 100 GB fast transfer, 4 active CPU hours and 360 GB-hours provisioned memory; it limits Hobby to non-commercial personal use. Compare the actual Vercel plan/bill and usage before claiming savings. Neon and LINE charges remain separate on either host. Railway account, real resource graphs, monthly traffic mix, container memory/CPU and egress are unavailable here; no actual cost saving is claimed.
