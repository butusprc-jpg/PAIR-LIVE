## Installed boundaries

- `/admin` mounts the Admin Auth login/session/logout components. Configured Admin Auth requires `DATABASE_URL`, `LINE_CHANNEL_ID`, `ADMIN_AUTH_ORIGIN`, and a server-only `ADMIN_AUTH_ALLOWLIST_JSON`. The separate module supplies hashed sessions, expiry, allowlist and one-use CSRF challenges. Missing/invalid config fails closed. `/api/admin/settings` and `/api/admin/round/tick` require admin/operator roles and mutation CSRF; `/api/admin/reports/daily` and `/api/admin/evidence` require an admin role for reads. Wallet grants and OCR confirmation remain closed. Real LINE Login is NOT TESTED without provider and database credentials.
- `/api/stream/publisher` requires admin/operator session plus mutation CSRF and a streamable round (`OPEN`, `CLOSED`, `SCANNING`, `REVIEW_REQUIRED`). The admin camera component can preview, switch, publish one video track using the existing LiveKit room, reconnect and release the track. Member viewer token and status routes also check round state. This is an implemented API/client path, **not a proven LiveKit integration**: no SFU URL, credentials or real device were available. The Round Worker now deletes the LiveKit room after SETTLED/CANCELLED before opening a new round; an SFU error blocks that transition. This policy is not verified against a real LiveKit service and an already-connected viewer can remain for up to the status-poll interval before the client disconnects. No production LIVE claim is made.
- `TrustedFrameSource` defines the server-attested LiveKit egress/frame adapter contract. There is no provider egress process, so OCR frame capture and settlement remain BLOCKED. `/api/ocr/confirm` checks admin role and CSRF, then returns 409 rather than accepting browser-supplied OCR or publishing an unverified result. Existing Tesseract fixture tests still verify the OCR engine, not camera capture.
- `S3EvidenceStorage` uses a private S3-compatible endpoint (including R2), content-hash keys, `If-None-Match: *`, bounded PNG input, server-only credentials and readback hash checks. Configure `EVIDENCE_S3_ENDPOINT`, `EVIDENCE_S3_REGION`, `EVIDENCE_S3_BUCKET`, `EVIDENCE_S3_ACCESS_KEY_ID`, `EVIDENCE_S3_SECRET_ACCESS_KEY` on the server. The bucket policy must deny public access. No credentials or bucket were available, so production object storage is NOT TESTED. Local/Fake storage tests are separate.
- Report Module accepts a decimal OCR display string without converting it to float; `136.20` retains its final zero. The module's CSV export is exposed through the role-guarded daily report endpoint. The PostgreSQL reader now derives evidence availability from verified evidence and uses a complete-entry read: an RLS-restricted reporting role fails closed rather than silently undercounting. Report tables require the imported migration. The existing module powers an opt-in `npm run notification:worker` process behind `NOTIFICATION_DELIVERY_ENABLED=true`; no settlement event is created without trusted OCR evidence. Email and WeChat transports stay disabled without verified provider configuration. LINE, email and WeChat delivery are NOT TESTED; no credential or transport is configured.
- Migration 006 adds persistent wallet phases `LEGACY`, `CUTOVER_PENDING`, `WALLET_ACTIVE`, `WALLET_SUSPENDED`. Database trigger permits only forward transitions and rejects legacy balance edits outside LEGACY. Core permits old debit only in persistent LEGACY with environment gate off; it permits Wallet debit only in WALLET_ACTIVE with both gates true. Other combinations fail closed. The migration defaults to LEGACY. Cutover and reconciliation require a separate approved deployment procedure and real PostgreSQL testing; they were not done.

## Security and production blockers

The HTTP routes deny unauthenticated member/admin requests; viewer tokens cannot publish, and publisher token issuance is role/CSRF guarded. Browser OCR text is never accepted as settlement data. Evidence reads require a member session and a SETTLED round. Secrets are referenced only in server modules. The remaining production blockers are a trusted LiveKit server egress adapter, a settlement transaction with evidence/audit/outbox, real admin and member provider credentials, LiveKit/SFU and TURN verification on devices, private object-store verification, PostgreSQL migrations and full RLS/concurrency tests, and edge rate limits. Until then, screenshots are development/login views, not evidence of production end-to-end success.
