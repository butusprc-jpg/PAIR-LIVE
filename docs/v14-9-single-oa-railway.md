# V14.9 single-OA Railway staging

This branch starts at V14.8. It does not include the unfinished multi-OA credential store, scoped webhook, nullable OA financial columns, or migrations 037–041 of Draft PR #15. No migration is required. The old financial and LINE routes remain unchanged.

## Isolated staging gate

The existing Railway project `5a54ffee-e6e9-49c9-945e-9f2225c8acf8` has a `staging` environment with `pair-live-web`, `pair-live-round-worker`, and an isolated Railway PostgreSQL template service. No LINE credentials are configured. Do not point either service at production Neon or real LINE credentials. Apply the migration manifest to the private staging database with the explicit staging guard; deployment must never run migrations automatically.

For a DB-only preview without LINE credentials set `RAILWAY_STAGING_NO_LINE=true` on Web. This mode accepts only `/api/health/ready` and returns 503 for every other `/api/*` endpoint, including login, webhook, wallet and all financial operations. It does not send LINE or start a round worker. The page shell can load, but member transactions cannot be exercised through this public preview. The staging migration command (`npm run db:migrate -- --staging-apply`, then `--staging-validate`) accepts only this Railway project/environment and a private `.railway.internal` database named `railway`. It is an explicit one-shot command, never a pre-deploy hook. Railway's staging PostgreSQL template has a self-signed TLS certificate; certificate verification is disabled **only** for this exact private staging target. Production and the existing local test guard retain their original TLS settings.

The existing Round Worker service may be used as a one-shot migration runner with `Dockerfile.railway-migrate` pinned to this SHA. Its round tick command must remain disabled. After reviewing successful apply/validate logs, leave the service stopped until authorized test LINE credentials exist, then restore `railway.json` and verify worker uniqueness before starting rounds.

Configure both services with the same test `DATABASE_URL`, `CONNECTED_LINE_OA_ID`, LINE Login/Messaging provider and channel IDs, secrets, and Messaging access token. Set `RAILWAY_SINGLE_OA_MODE=true` on both. Configure a test LIFF ID and the public build arguments `NEXT_PUBLIC_LINE_LIFF_ID` and `NEXT_PUBLIC_APP_BASE_URL` on Web. Secrets are runtime variables, never Docker build args. Keep `PAIR_WALLET_CUTOVER_VERIFIED=false`, `NOTIFICATION_DELIVERY_ENABLED=false`, and `TOPUP_CLEANUP_ENABLED=false` until their existing gates are reviewed. Use `railway.web.json` for Web and `railway.json` for the single Round Worker; one replica each. The web health route returns 503 if the OA is not uniquely enabled and token-bound, if provider IDs differ, or if channel secrets or LIFF ID are missing. The worker checks the same binding before startup and each tick. The existing Owner mutation holds a transaction-scoped advisory lock and rejects enabling a second OA. Keep the branch pinned by commit SHA and disable auto-deploy.

Verify the Messaging token against the intended test OA using LINE's server-side bot info before binding its SHA-256 in the owner control plane. Verify that Login and Messaging channels share the intended provider and that the LIFF ID belongs to the test Login channel. The static preflight and database hash cannot independently prove a secret or LIFF ID belongs to the channel; this requires authorized test credentials. Do not send a LINE message simply to test configuration.

When the isolated database and authorized synthetic/test credentials exist, deploy Web and Worker to the existing staging services only. Confirm Web `/api/health/ready`, worker logs, one active replica, restart, and no duplicate round tick across restarts. Test login, LIFF and Rich Menu on an authorized test OA/device; test VDO.Ninja only with an authorized camera. Never claim those flows passed from CI mocks. Do not change production endpoints or DNS. For rollback stop Worker first and revert both services to the previous staging deployment; do not run two workers against the same database.
